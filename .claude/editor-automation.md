# エディタ操作のコマンド化 — 設計

AI(Claude Code 等)と人間の両方がエディタを扱いやすくするための設計文書。

- 対象: KujataEngine のエディタ(`KujataEngine/Editor/`)と、起動・ログまわり(`base/`)。
- 状態: **設計のみ。実装は未着手。**
- 関連: [CLAUDE.md](CLAUDE.md) の「現在の方針」②(決定論+リプレイ)、[determinism.md](determinism.md) の Step 4(入力の記録・再生)

---

## 1. なぜ必要か

今のエディタは「人間が画面を見てマウスで操作する」ことしか想定していない。
AI に作業させると、次のところで詰まる(2026-09 の作業で実際に起きたこと)。

| 困りごと | 今の回避策 | 問題 |
|---|---|---|
| オブジェクトを選べない | スクリーンショットから座標を割り出してクリック | レイアウトが変わると同じ座標では押せない |
| 結果を確かめられない | ウィンドウを撮影して画像を目で見る | 値の確認ができない。見落としやすい |
| キーが押せない | OS へのキー注入 | Release では届かない |
| ログが読めない | ファイルの `logs/` だけ | エディタの Console の中身は外から読めない |
| 起動確認が手作業 | 起動 → 何秒か待つ → 強制終了 を毎回組み立てる | 待ち時間の勘に頼る。失敗を終了コードで判定できない |

人間にとっても似た不便がある: Undo の履歴に何をしたかが出ない、Console を絞り込めない、
シーン JSON の git 差分が ID の揺れで読みにくい、不具合を他人の PC で再現できない。

## 2. 方針: 操作を 1 つの「コマンド層」にまとめる

AI 専用の仕組みを別に作らない。**エディタの操作をコマンドとして 1 か所にまとめ、
人間の UI も AI もスクリプトも、そこを通す**。入口が違っても中身が同じなので、
どちらから見ても同じ名前・同じ結果・同じエラー文になる。

```
 人間:   メニュー / ボタン / ショートカット / コマンドパレット ─┐
 AI:     外部からの JSON コマンド(MCP 経由) ─────────────────┼→ コマンド層 → Scene
 スクリプト: コマンドライン(バッチ実行) ────────────────────┘
                                   (Undo・ログ・入力チェックはコマンド層で一括して行う)
```

### 守る決まり

1. **名前は 1 つに揃える。** Inspector の表示名・JSON のキー・コマンドで使う名前を同じにする。
   人間が「MonsterBall の Rotator の Speed を上げて」と言えば、そのまま AI のコマンドになる。
2. **オブジェクトはパスでも指定できる。** GUID(instanceId)に加えて `Stage/Enemies/Guardian` のような階層パスを受け付ける。
   同名が複数あるときは曖昧だとエラーを返す(黙って先頭を選ばない)。
3. **失敗の理由は文章で返す。** 画面に出す文とコマンドの返り値を同じにする
   (例: 「Local Volume には Collider が必要です」)。
4. **変更は必ず Undo できる。** 1 回の依頼(=1 コマンド、または明示したまとまり)を 1 回の Undo で戻せる。
5. **AI の変更は見えるようにする。** 外部から来たコマンドで変わったオブジェクトを Hierarchy で一時的に強調し、
   Undo の履歴にも出所(Editor / External / CLI)を付ける。削除などの大きな操作は既定で確認を挟む。

## 3. 機能の一覧

実装順(§5)とは別に、機能ごとの中身をまとめる。

### A. バッチ実行(コマンドライン)

起動時に指示を渡して実行させ、終わったら自分で終了する。

```
KujataEngine.exe --project DirectXGame --scene Stage1 --play-frames 300 ^
                 --screenshot game.png --dump-state state.json --log-json log.jsonl --exit
```

| 引数 | 動作 |
|---|---|
| `--scene <名前>` | 起動シーンを指定する(StartupScene.txt より優先) |
| `--play-frames <N>` | 自動で Play に入り、N フレーム進めてから次へ |
| `--screenshot <パス>` | Scene / Game ビューの**描画結果(RT)を PNG に書き出す**。ウィンドウの撮影ではないので、隠れていても・画面外でも撮れる |
| `--dump-state <パス>` | その時点のシーン状態を JSON で書き出す(C 参照) |
| `--log-json <パス>` | ログを JSON Lines でも書く(D 参照) |
| `--exit` | 上の処理が終わったら終了する |

- 終了コード: 0 = 正常、それ以外 = 失敗(シェーダーのコンパイル失敗、シーン読み込み失敗、assert、エラーログあり 等)。
- ユニットテストを運用しない方針なので、「ビルド成功+実機起動」の確認を**人間も AI も同じ 1 行で回せる**ことが目的。
- 人間向けには、Build メニューに「チェック実行」を置き、同じ処理を呼ぶ。

既存: `--project` の解析は `base/ProjectPath.cpp` にある。同じ場所に引数の解析をまとめる。

### B. コマンド層と外部からの窓口

- エディタ内に `EditorCommand`(名前・引数・実行・Undo のラベル)を登録する仕組みを作る。
- 起動中のエディタに**名前付きパイプ**(またはローカル HTTP)で JSON を送ると、コマンドを実行して JSON で結果を返す。
  - 受信は別スレッドでも、**実行はメインスレッドのフレームの頭**(`EditorApplication::Update` の先頭、`ProcessPendingSceneChange` と同じ位置)で行う。描画中にシーンを触らないため。
- これを MCP サーバーとして包めば、Claude Code からツールとして直接呼べる。

最初に用意するコマンド(案):

| 分類 | コマンド |
|---|---|
| 参照 | `scene.list`(オブジェクト一覧・階層) / `object.get`(フィールド値) / `schema.get`(型情報) / `log.tail` / `selection.get` |
| 編集 | `object.create` / `object.delete` / `object.rename` / `object.setParent` / `component.add` / `component.remove` / `field.set` / `prefab.instantiate` |
| 実行 | `play.start` / `play.stop` / `play.step`(N フレーム進める) / `scene.save` / `scene.open` / `module.reload`(Reload DLL) |
| 確認 | `view.screenshot` / `state.dump` / `selection.set` |

- 人間向けには、同じ登録簿から **コマンドパレット**(Ctrl+P でコマンド名を打って実行)を作る。
- 今あるメニュー・ボタン・ショートカットは、一度に作り直さず、**少しずつコマンド層を呼ぶように置き換える**。

### C. 型情報と状態の書き出し

- `SerializedFieldRegistry` は Mode(DrawInspector / WriteJson / ReadJson / ...)を切り替えて同じ登録から動く作りなので、
  **`Mode::DescribeSchema` を足す**と、コンポーネントごとのフィールド名・型・範囲・既定値・ツールチップを JSON にできる。
  - AI は「何を設定できるか」を推測しなくて済む。
  - 人間向けには、同じ情報を Inspector のツールチップ・範囲チェックに使う(表示と検査の食い違いが無くなる)。
- `state.dump` はシーンの全オブジェクトについて、パス・有効/無効・コンポーネントとフィールド値を書き出す。
  既存の `Scene::ToJson` をベースにし、パスを足した読みやすい形にする。

### D. ログの構造化

- `Logger` / `EditorConsole` の出力を、テキストに加えて **JSON Lines**(1 行 1 件: 時刻・レベル・分類・メッセージ・関係するオブジェクトのパス)でも書けるようにする。
- 人間向けには、Console をレベル・分類で絞り込み、行をクリックすると関係するオブジェクトを選択できるようにする。

### E. Undo の履歴を見えるようにする

- 今の `EditorUndoManager` はシーン全体の JSON スナップショット+ラベルで持つ方式なので、
  **ラベルを「何を・どう変えたか」にする**だけで履歴が読めるようになる(例: `MonsterBall/Rotator.speed 0.02 → 0.05`)。
- 履歴一覧ウィンドウを作り、出所(Editor / External / CLI)を表示する。
- 1 コマンド=1 スナップショットにして、AI の 1 回の依頼を 1 回の Undo で戻せるようにする。

### F. 固定 ID とパス

- 今のインスタンス ID は `GameObject.cpp` の `GenerateInstanceId()` が**時刻と乱数**から作るので、
  同じ操作をしても ID が変わり、シーン JSON の差分が毎回ぶれる(determinism.md の #3 と同じ問題)。
- シーン内の連番など、決まった規則で ID を振るようにする。git の差分が「本当に変わったところ」だけになる。
- パス(`親/子/孫`)で引けるように、`Scene` にパス検索を足す。

### G. 入力の記録・再生(決定論と共通)

- 入力を OS から直接読むのをやめ、記録・再生できる層を挟む(determinism.md の Step 4)。
- AI はこの層に入力列を渡せばよく、OS へのキー注入が要らなくなる(Release でキーが届かない問題も消える)。
- 人間向けには、不具合の報告に再生ファイルを添えて、誰の PC でも同じ現象を再現できる。
- 決定論が入れば、「この入力列で N フレーム回した状態のハッシュ」を比べて、変更の前後で挙動が変わっていないかを確かめられる。

## 4. 人間から見た効果のまとめ

| 仕組み | AI が得るもの | 人間が得るもの |
|---|---|---|
| バッチ実行 | 起動確認を自動で回せる | 「チェック実行」を 1 回押すだけで確認できる |
| コマンド層 | 座標を探さずに操作できる | コマンドパレット、操作の一貫性 |
| 型情報 | 設定できる項目が分かる | ツールチップ・範囲チェック |
| ログの構造化 | ログを読んで原因を追える | Console の絞り込み、原因のオブジェクトへ移動 |
| Undo の履歴 | 自分の変更を戻せる | AI が何を変えたか確かめて戻せる |
| 固定 ID | 差分で結果を確かめられる | git のレビューが読める |
| 入力の記録・再生 | キー注入が要らない | 不具合の再現ファイルを共有できる |

## 5. 実装の順番

| Step | 内容 | 理由 |
|---|---|---|
| 1 | A のバッチ実行(`--scene` `--play-frames` `--screenshot` `--exit` と終了コード) | 小さく作れて、すぐ全員の確認作業が楽になる |
| 2 | D のログの構造化 と C の `state.dump` | 画像ではなくテキストで結果を確かめられるようになる |
| 3 | B のコマンド層(参照系のコマンドから)+ コマンドパレット + E の Undo ラベル | 読むだけのコマンドは壊す心配がないので先に作る |
| 4 | B の編集・実行系コマンド、MCP サーバー、C の `schema.get` | AI がエディタを直接操作できるようになる |
| 5 | F の固定 ID、G の入力の記録・再生 | 決定論の作業(determinism.md)と一緒に進める |

## 6. 決めていないこと

- 外部からの窓口を名前付きパイプにするかローカル HTTP にするか(MCP サーバーから繋ぎやすい方を選ぶ)。
- 外部からのコマンドを、Play 中にどこまで受け付けるか(編集系は Edit 中だけにする案)。
- 配布ビルド(エディタ UI なし)でバッチ実行をどこまで使えるようにするか。
